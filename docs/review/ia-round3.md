## 0. 先回答两个问题

### Q1 哪些独立页面可以聚合？

**6 处该并，4 处不该并。净效果：路由 20 → 19（只有 pay+fund 真正并掉一条），但入口数 18 → 14、`/account` 4 tab → 2、`/shop` 3 tab → 1 页 + 2 弹层、`/pay` 三处并成 3 tab。**

> 说明：多数合并**不减少路由**（详情页要留深链），减少的是**入口、tab 与重复控件**——那才是用户迷路的成本所在。

| 合并 | 现状 | 并成 | 为什么 | 成本 |
|---|---|---|---|---|
| **① 用户域** | `/users`（整页一个输入框）+ `/account?tab=ban`（被封禁用户列表） | `/users`（列表 + 搜索）+ `/users/:id`（详情），`?filter=banned` | 封禁列表返回的就是「用户数组」，它是**用户列表的一个筛选**，却被挂在账号页下，还被 3 个地方链接 | 中 |
| **② 资金域** | `/pay`（服务商+收支+查单+转赠）+ `/fund`（基金订单）+ `/account?tab=carrot`（余额+流水+转赠） | `/fund?tab=merchant\|fund\|carrot`（或 `/money`） | 三者共享「胡萝卜」这一个对象；**"让胡萝卜从我这儿出去" 现在有 3 个入口**（pay 转赠 / account-carrot 转赠 / fund 发放）；都是「低频配置 + 高频查账」 | 低（纯拼装） |
| **③ 商品/店铺** | `/shop` 3 tab（商品/分类/店铺），商品 tab 内还有第二排分类 chips | `/shop` 1 页（商品+分类 chips），分类管理进「管理分类」弹层，店铺信息移出 | 分类是商品的**筛选维度**不是同级实体；店铺是**配置**不是内容。现在同屏两级 tab 共 4~7 个 tab 形控件 | 低（同文件重排） |
| **④ 账号瘦身** | `/account` 4 tab（资料/邀请/胡萝卜/封禁） | `/account` 2 tab（资料 / 邀请），胡萝卜→资金域、封禁→用户域 | 4 个 tab 是 4 个域：设置、社交、账务、审核。它们不共享任何对象 | 低 |
| **⑤ 回收站降级** | 侧栏独立项 `/recycle` | 保留路由，去侧栏；媒体库页头给「回收站 (N)」 | 回收站是媒体库的状态筛选（`videoApi.list({only_delete})` / `mediaApi.listAll({only_delete})` 都已支持） | 极低 |
| **⑥ 悄悄话归位** | 在「系统」组，与「求片」同图标同语义 | 移到「内容」组，与求片相邻 | 它是内容互动消息，不是系统配置 | 极低 |

**4 处明确不建议合并**（合并会变差，不是变好）：

| 不并 | 理由 |
|---|---|
| `/upload` ✕ | 重流程：tus 分片 + 队列 + 暂存区，是页面级工作区，不是列表 |
| `/library` ✕ | 它是全站的「锚点页」，合并会毁掉导航心智 |
| `/live` + `/lines` ✕ | 一个管频道内容（有 post/源），一个管反代候选（无内容），实体不同 |
| `/orders` ✕ | 它是**每天都要看**的高频运营页；虽然和 fund 都叫「订单」，但一个是商品交易、一个是活动发放，实体不同 |

> 关于 `/seek` + `/whisper`：**不建议并成一个页面**（实体不同，并了只是并排两套表格，还把深链弄坏），但**建议让「概览」承接它们的行级动作**——真正的合并点不是"页面合并"，而是"待办视图合并"。见 §2。

### Q2 概览能否承载快捷操作？

**能，而且这是本轮性价比最高的一件事。但现在的「快捷入口」卡是假的：4 个链接里 2 个都去 `/account`，0 个真正执行动作。**

一句话规格：**概览 = 待办行（能就地处理）+ 我的状态（能就地执行）+ 运维小工具（弹层/行内表单），纯导航链接全部删掉。**

预期结果：**首屏可完成 6 个真实动作**，并因此可以取消 4 个入口（封禁列表、查单卡、转赠入口 ×2、查用户整页）。详见 §2。

### 2.2 六个合并的详细判断

**① 用户域：`/users` 是「一页一个输入框」，这是全站最贵的浪费**

`UserSearchView.tsx` 89 行：H1「查用户」+ 一张卡（一个 input + 查询按钮 + 说明）+ 一张卡（最近封禁 5 条）。**首屏 90% 面积在等用户敲 4 个字符。**

而封禁列表在三个地方被链接（`UserSearchView.tsx:25`、`:62`、`UserDetailView.tsx:29` 都指向 `/account?tab=ban`），说明它本来就是一个独立视图，只是暂住在账号页。

**建议**：
```
/users?q=&filter=all|banned|invited
├ 工具条：搜索框（ID / 用户名 / Telegram）+ 筛选 seg
├ 结果表：用户 / 状态(封禁?) / 邀请人 / 注册 / 最近活跃 / [解封|查看]
└ 空态：一句「输入用户 ID 查询」+ 最近封禁 5 条（现内容保留为默认态）
```
- 搜索数据源已存在：`payApi.userInfo({user_id|username|telegram_user_id})`（最全）、`inviteApi.history({username|user_id})`、`banApi.list()`、`shopApi.ordersShop({user_id})`。
- **`/users/:id` 不动**：订单表里的用户名已经链到这里（`OrdersView.tsx`），它是深链目标。
- 收益：删掉「查用户」这个纯输入页，封禁列表从账号页归位，`/account` 顺势 4 tab → 3 tab。

**② 资金域：三个页面 + 三个转赠入口**

| 页面 | 现在有什么 | 本质 |
|---|---|---|
| `/pay` | 累计收入/支出、回调地址、查单、转赠 | 支付**通道**配置 |
| `/fund` | 基金订单列表、新建订单、提交凭证 | 活动**发放**对账 |
| `/account?tab=carrot` | 余额、变动记录、转赠 | 我的**钱包** |

三者共享同一个对象（胡萝卜），却各占一个侧栏项。**转赠有 2 套实现**（`PayView.tsx:117-152` 的三个控件挤一行、`AccountView.tsx` 的 Modal + 说明），校验与文案都不一样；再加上 `fundApi.create` 的发放，一共 3 处"往外给胡萝卜"的入口。

**建议**：合并为 `/fund`（更准的名字是 `/money`）3 个 tab：
- **服务商**：`payApi.base` 的收支 + 回调地址 + 申请/编辑/测试回调（`payApi.testNotify` 已有端点，现在没人用）
- **基金**：`fundApi.orders` 列表 + 新建 + 提交凭证（现 FundView）
- **胡萝卜**：余额 + 变动 + **转赠（唯一入口）**（从 account/carrot 搬来）

顺带清理：`payApi.close`、`payApi.create`、`payApi.userCarrot`、`redPacketApi`、`lotteryApi` 这些端点在 UI 上完全没有入口——要么接进来（放在"服务商"tab 的工具区），要么明确标注为"暂不支持"。

**③ 商品/店铺：`/shop` 一屏两级 tab**

`ShopView.tsx:62-97` 是页面级 3 tab；`:84-100` 是商品 tab 内的第二排分类 chips + 「新增商品」主按钮。**两排长相相同、间距 0，用户看到的是 6 个同级 tab**（第二轮已记录，未修）。

**建议**：
- 分类 chips 保留（它是筛选，属于工具栏）
- 「分类」tab → 商品页右上「管理分类」弹层（增删排序：`shopApi.createCategory/deleteCategory/sortCategory` 全有）
- 「店铺」tab → 移到 `/account` 的「我的店铺」区块（`shopApi.sellerBase/apply/update`），或并入资金域的"服务商"tab——**商户身份只有一处**

**④ `/account`：4 个域挤在 4 个 tab**

```
账号
├ 资料   3 张统计卡 + 笔名 + 开关 + 4 个权限位 + 5 个 ghost 按钮   ← 8 个可交互元素
├ 邀请   名额/邀请用户/邀请记录表/邀请关系树                       ← 2 表 + 1 表单
├ 胡萝卜 余额/转赠/变动记录表                                    ← → 资金域
└ 封禁   封禁列表                                                ← → 用户域
```
**建议**：`/account` 只留 **资料 / 邀请**；胡萝卜搬资金域、封禁搬用户域。profile tab 内部再分两块（「身份」= 笔名+权限位；「安全」= 密码 + 登录策略），把 5 个 ghost 按钮拆到对应块。

**⑤ 回收站**：路由保留（恢复动作需要地方落），但侧栏 18 → 17 的第 1 刀就砍它。媒体库页头加 `[回收站 36 万]` 链接；`/recycle` 的两 tab（资源/影片）保留。

**⑥ 悄悄话**：从「系统」移到「内容」，与求片相邻。两者图标现在都是 `IconInbox`（撞车），见 §5。

## 3. 概览快捷区设计（到可实现粒度）

### 3.1 现状盘点

概览现在有 **10 个数据请求**（`useCapabilities` 内含 session + sellerBase、carrot、continueWatching、watchStats、carrotHistory、myWatches、todos×3）——其中 `/api/carrot/current` 实测 20s 超时、`/api/ban/list` 5–11s（`SPEC-UI.md:60`）。**再加功能必须先解决"加什么就有哪些请求"**，否则首屏会更慢。

好消息：**要加的动作，数据都已经在请求里了**，只需要把 `page_size` 从 1 改成 3。

### 3.2 目标布局（首屏 3 行）

```
┌ 页头：概览  ·  11 月 2026  ·  晚上好，xxx [今天还没看片…]
├ ① 待处理（最多 3 组，每组 1 行展开 + 其余折叠）
│   [求片 3]《沙丘 2》5 人求 · 悬赏 120  [认领]        ← 行内按钮，就地消失
│   [发货 2]#20261104001 · ¥68 · 2 天前  [发货]        ← 行内按钮
│   [悄悄话 4]「第 3 集有字幕吗」         [回复]        ← 弹层
├ ② 我的（3 卡）
│   [签到] 连续 12 天           [立即签到]  ← 直接执行（已有）
│   [胡萝卜 12,340] 距下一境 660  [兑换槽位] ← 直接执行（watchApi.slot）
│   [我的上传 42.1 GB] 累计      [去上传]    ← 导航（重流程，必须离开）
├ ③ 运维工具（仅 isMerchant || isAdmin 渲染）
│   [新建基金订单] 活动码 [______] 胡萝卜 [100] [创建]   ← 行内表单
│   [支付查单]     订单号 [______] [查询] → 就地展开 4 字段 ← 行内表单
│   [转赠胡萝卜]                                          ← 弹层
└ ④ 继续观看 / 我的近况 / 我的片单（看，不是做——下沉到第 2 屏）
```

### 3.3 逐卡规格

| 卡 | 内容 | 触发方式 | 端点 | 成功后 | 失败后 |
|---|---|---|---|---|---|
| 待认领求片 | 3 条：片名 · 求片数 · 悬赏 | **行内按钮**「认领」 | `seekApi.claim(id,'confirm')` | 行淡出 + toast「已认领」+ 计数 -1；全空则整组消失 | toast 带状态码（全局 `MutationCache.onError` 已兜底）+ 行内 `aria-busy` 复位 |
| 待发货订单 | 3 条：订单号 · 金额 · 付款时间 | **行内按钮**「发货」 | `shopApi.delivery(no, true)` | 同上 | 同上 |
| 待回复悄悄话 | 3 条：内容摘要 · 来自 | **弹层**（需输入正文） | `whisperApi.reply(id, content)` | 关闭弹层 + toast | 弹层内保留输入 |
| 签到 | 连续天数 | **直接执行**（已有） | `userApi.sign()` | 卡片就地变「今天已签」 | 「今天已经签到过了」 |
| 胡萝卜 + 槽位 | 余额 · 境界 · 槽位 | **直接执行**「兑换槽位」 | `watchApi.slot()`（无参数、幂等性由后端保证） | toast「剩余 N 槽位」+ 卡内数字更新 | toast 说明胡萝卜不足 |
| 我的上传 | 累计体积 | **导航**（唯一保留的纯入口） | — | — | — |
| 新建基金订单 | 活动码 + 胡萝卜 | **行内表单**（3 个控件，不进弹层） | `fundApi.create(code, carrot)` | toast「已创建 {no}」+ 表单清空；不跳页 | 表单保留，错误行内提示 |
| 支付查单 | 订单号 | **行内表单 + 就地结果** | `payApi.query(no)` | 卡内展开 金额/状态/方式/时间 4 行 `kv` | 「没有查到这个订单」一行 `card-note` |
| 转赠 | 对方 ID + 数量 | **弹层**（2 个输入 + 不可撤销提示） | `carrotApi.transfer` | toast「已转赠，余额 N」 | toast + 保留输入 |

### 3.4 数据层改动（唯一必要的）

```ts
// queries.ts: useTodos 从"只取 total"升级成"取 3 条 + total"
seekApi.list({ status:['default'], page:1, page_size:3 })      // 原来 1
shopApi.ordersShop({ page:1, page_size:3, is_pay:'true', is_delivery:'false' })
whisperApi.receiver()                                          // 新增（返回数组，取前 3）
banApi.list()                                                  // 保持（只算长度）
```
- **请求数 10 → 11**（只多一个 whisper），且全部走 `['todos']` 同一个 60s 缓存。
- 每类互相独立（`Promise.all` + `safe` 包裹已实现），任一慢/挂不阻塞其他——符合 `SPEC-UI.md:58` 的"一个慢接口不能阻塞整页"。
- 若嫌 whisper 重（返回全量数组），退一步：本期的"待回复悄悄话"只显示计数，不做行内回复。

### 3.5 因此可以取消的入口

| 取消 | 现在在哪 | 取消后 | 原页面怎么办 |
|---|---|---|---|
| 封禁列表 | `/account?tab=ban`（3 处链接） | 概览「封禁中 N 人」→ `/users?filter=banned` | Account 删 tab；`/users` 承接列表 |
| 支付查单 | `/pay` 第二卡 | 概览运维区行内查单 | `/pay`（并成资金 tab）只剩服务商配置 |
| 转赠 | `/pay` + `/account?tab=carrot`（2 处） | 概览运维区弹层（唯一入口） | 两处删除，避免三套校验 |
| 查用户整页 | `/users` | 概览待办里的用户名直接链 `/users/:id`；全站搜索进侧栏 ⌘K | `/users` 变列表页（见 §2①） |
| 快捷入口卡 | 概览现有 4 个纯导航 link | **删除**（4 个目标全被侧栏 + 「我的」卡覆盖） | — |

### 3.6 概览还应拿回的两个"运营态"

`queries.ts` 里 **`usePlayingNow`、`useRankUpload`、`useSeekOpen`、`useZoneCounts` 四个查询现在 0 引用**（全是死代码，且最后一个 `refetchInterval: 30_000` 还在跑）。
- 建议：`usePlayingNow`（正在播放 N 路，30s 轮询）放进运维区做**只读一格**——这是唯一能回答"这台实例现在活得好不好"的信号。
- `useZoneCounts`（片库总量/电影/剧集）不必上概览——媒体库页头 `12 万 部` 已经承载。
- 其余两个删掉（`useSeekOpen` 已被 `useTodos` 取代、`useRankUpload` 无 UI）。

### 3.7 首屏预算核对

## 5. 侧栏精简方案

### 5.1 现状四个问题

1. **图标撞车 3 组**（16 个链接只有 13 个不同图标，另有 2 个分区用来当「圆点」）：
   - `IconWallet`：基金 / 支付
   - `IconUser`：查用户 / 账号
   - `IconInbox`：求片 / 悄悄话
   → 侧栏图标的第一功能是**快速定位**，撞车等于没有图标。
2. **「系统」组 7 项**，是杂物抽屉：线路 / 回收站 / 查用户 / 基金 / 悄悄话 / 支付 / 账号。7 项已到扫读上限，且组内没有任何共同点。
3. **「内容分区」2 行是媒体库的 tab**（电影/剧集），`Sidebar.tsx:118-140`。它和「媒体库」重复，还占 2 行 + 一个组标题。
4. **`chev: true` 的片单/账号带尖括号，点了不展开**（第二轮已记录，未修）；`⌘K` 键帽仍在，全仓无快捷键实现（`grep metaKey` = 0）。

### 5.2 目标：18 行 → 14 行

```
内容           运营            系统
概览           上传            线路
媒体库         直播            用户        ← 合并「查用户」+ 封禁
片单           商城            资金        ← 合并「支付」+「基金」
求片           订单            设置        ← 原「账号」，去掉胡萝卜/封禁
音乐
悄悄话  ← 从系统移来
```
- **6 + 4 + 4 = 14 项**，3 组（原 16 项导航 + 2 项内容分区 = 18 行）。
- 移出：内容分区 ×2（电影/剧集并进媒体库 tab）、回收站 1 行（进媒体库页头）、支付与基金合并省 1 行；另有两处是**改名**不是删除：查用户 → 用户（承接封禁）、账号 → 设置（去掉胡萝卜/封禁）。
- 若采纳"悄悄话并入求片成「互动」"，可再省 1 行 → 13 行。
- 图标去重：资金用 `IconWallet`、用户用 `IconUser`、设置用 `IconGear`（需新增）、悄悄话用 `IconMessage`（需新增，别再用 Inbox）。
- `chev` 要么接展开（片单 → 最近 3 个片单；设置 → 4 个 tab 直达），要么删掉。

### 5.3 顺带解决：⌘K 命令面板（把三个搜索框合成一个）

现在全站有 **3 个搜索入口**且各管一摊：侧栏搜片名（→ `/library`）、`/users` 页搜用户 ID、`/recycle` 搜媒体 ID/用户 ID。而侧栏那个键帽 **`⌘K` 是假的**。

建议用 1 个命令面板承接全部四种跳转：**片名 / 用户 / 订单号 / 媒体 ID**，命中后直接进详情。这样：
- `/users` 可以彻底变成列表页（不再需要"输入框页"）
- 侧栏搜索框保留（它等于 ⌘K 的常驻形态），placeholder 改成「搜索片名、用户、订单号」
- 键帽从谎言变成功能

实现成本：低（`asString` 等 search 工具已在 `lib/search.ts`；四个数据源端点都已存在）。

### 5.4 侧栏还应加的一个东西：待办徽标

`NavItem` 已有 `tail?: string` 字段但**从未被赋值**（`.rail__tail` 的 CSS 也一直空转）。`useTodos` 已经返回求片/订单/封禁计数，接上即可：

```
求片  [3]     订单  [2]     用户  [1]
```
这是侧栏最该有的信息——**不必点进去就知道哪里有事**。而且是纯前端接线，零新请求（用同一个 `['todos']` 缓存）。

## 7. 需要拍板的三个取舍

1. **`/pay` 改名吗？** 合并后它同时管"支付通道 + 基金订单 + 我的胡萝卜"，叫「支付」名不副实。建议 `/fund` 保留路由、导航文案叫「资金」；或新路由 `/money` 并给旧路径 301。
