# EMOS 管理台 · 功能与信息架构审查

> 只读审查，未改动 `src/` 任何文件。范围：`src/router.tsx`、`src/components/Sidebar.tsx`、`src/views/*.tsx`（16 个视图）、`src/api/endpoints.ts`（24 域 / 184 个方法）、`src/api/queries.ts`（45 个 hook）。每个端点都核对过 UI 侧是否有入口。
>
> 口径：
> - **无入口** = `endpoints.ts` 已封装，但 `queries.ts` 与 `views/` 里都找不到引用。
> - **死控件** = 渲染出来了、有文案有图标，但没有 `onClick` / `onChange` / 对应路由。
> - 红包 / 抽奖 / Telegram 投票 / 基金 / 悄悄话 / 影院 6 个域（23 个端点）按 README 说明「有意不做」，不计入缺口。
> - 真实体量：片库 209,486 部、音乐 523,369 首、片单 260 个、直播 77 频道、线路 1,279 条。
>
> 统计结果：**89 个端点无任何 UI 入口，其中 68 个落在本审查域内**；9 处死控件（按钮/勾选框/输入框）；3 条主链路全部断在「做完了然后呢」。全文 101 条问题（P0 16 / P1 56 / P2 29，其中 4 条 P0 为跨章节交叉引用）。

---

## 结论先行

1. **导航是按「模块归属」排的，不是按「每天做什么」排的。** 每天要碰的求片、上传、订单分散在三个组、四个位置，而一年动两次的「支付」「线路」和它们同级。首页第一屏是「片库总量 / 分区构成 / 我的胡萝卜」—— 全是周会看的存量数字，没有一条需要动手的事。
2. **首页没有待办区，这是最大的信息架构问题。** 「待处理求片」只是个不可点的数字；待发货订单、待审核店铺、上传失败、异常直播源一个都不在。管理员每天上班的第一动作变成「挨个页面翻一遍」。
3. **三条主链路都断在最后一步之前**：上传入库完成只弹一个 toast；求片认领完成只弹一个 toast；订单发货完成只弹一个 toast。三处都是当天最高频动作，三处都没有「下一步去哪」。
4. **恢复能力不存在，但文案承诺了它。** 删除影片/删除资源的确认框写着「可从回收处恢复」，全站没有回收站 —— `mediaApi.restore`、`mediaApi.listAll(only_delete)` 都封装好了，没有入口。误删 = 资源真丢（重传再扣一次胡萝卜）。
5. **「用户」这一维整个缺失。** 订单里的用户名、求片里的认领人、封禁列表、邀请记录、胡萝卜流水里的 `user_id` 全都不可点，也没有 `/users/:id` 路由。客服工单（充值没到账 / 被误封 / 被顶号）100% 要从用户出发，现在 100% 走不通。
6. **危险操作和常规操作等权重，同时又藏得太深**，两个方向同时错位：影片详情页头「删除 / 同步 / 返回列表」三个同级 ghost 按钮；而「删除订单」藏在「备注」弹窗的 footer 左侧、「删除资源」藏在「重命名资源」弹窗底部。
7. **界面对外承诺了至少 5 项不存在的能力**：「搜索片名、用户名或编码」（侧栏）、「收起侧栏」、「新增入库」、「每 30 秒刷新」（求片）、「可从回收处恢复」。死控件比缺失更伤信任 —— 管理员会反复点。

## 一、主次功能划分：每天 / 每周 / 偶尔

### 1.1 管理员每天最常做的 5 件事

判定依据：真实数据体量与状态机（有「待处理」状态的才可能每天做）+ 端点的写操作密度。

| # | 每天做的事 | 为什么是每天 | 现在在哪里 | 顺手吗 |
|---|---|---|---|---|
| 1 | **处理求片**（认领 / 催片 / 看新求片） | 有 `default→upload→complete` 状态机，求片会持续流入；概览自己在统计「待处理求片」 | 内容组第 4 项，无角标、无自动刷新、无搜索 | 不顺手（最该置顶的一项排最下） |
| 2 | **上传入库**（收片、转存、补资源） | `recognize → save → 入库`，是内容生产的唯一入口；胡萝卜按次结算 | 运营组第 1 项，但首页完全没有它的位置，与「媒体库/求片」跨组割裂 | 半个（组放错了） |
| 3 | **媒体库排障**（找片、看资源/字幕、删错传的） | 209,486 部的存量，每天都在被传错、传重、传缺 | 内容组第 2 项 | 位置对，但列表有 5 处死按钮 + 2 个空转勾选框、行内无操作 |
| 4 | **订单发货** | 有 `待支付/待发货/已发货` 状态机 + 用户催单计数 | 运营组第 4 项，只能靠页面内「待发货」页签筛 | 不顺手（首页看不到待发货数） |
| 5 | **客服处理**（查用户余额 / 解封 / 顶号踢设备 / 邀请关系） | 订单、求片、封禁、邀请四个域的 `user_id` 全部指向这里 | **不存在**（账号页只能看「我自己」） | 走不通 |

### 1.2 三档频次表

| 档位 | 功能 | 数据依据 | 现在的位置 | 错配 |
|---|---|---|---|---|
| **每天** | 求片、上传入库、媒体库检索、订单发货、客服查用户 | 状态机 + 流入量 | 分散在 3 个组 | 严重 |
| **每周** | 片单维护（260）、直播源巡检（77）、线路巡检（1,279）、音乐补资源（52 万首中的无资源部分）、店铺/商品维护 | 存量维护类 | 运营/内容/系统各一组 | 中等 |
| **偶尔** | 支付配置、邀请名额、新建线路、分类整理、密码/安全 | 一次性配置 | 系统组 | 基本合理 |

### 1.3 错配清单

- **[P0] 首页（OverviewView）** — 第一屏放的是「片库总量 / 分区构成 / 我的胡萝卜 / 上传榜 / 正在播放」，全是存量或他人数据，没有任何「待我处理」 — 管理员每天上班要先挨个进求片、订单、直播页确认有没有事，三到五次页面跳转，且一定会漏（求片页还不自动刷新） — 首页改成「待办 / 今日 / 存量」三段，第一屏给可点的待办清单（见第七节表 B）。
- **[P1] 首页（OverviewView）· 「待处理求片」卡片** — 有数字但没有 `onClick`，`StatCard` 也不接受链接 — 看到「待处理 N 条」后必须自己找到求片页、再选「求片中」页签 — 卡片整块可点，直链 `/seek?tab=default`。
- **[P0] 订单（OrdersView）** — 不在首页，也没有角标，只能靠记住「订单页有待发货页签」 — 「今天有几单要发」这个每天必答的问题没有一处能一眼看到，漏发会导致用户催单（`urge_number` 已经在统计了，说明漏发在真实发生） — 首页待办区给「待发货 N 单」并直链 `?delivery=pending`。
- **[P1] 侧栏（Sidebar）· 求片排序** — 求片排内容组第 4 位，在片单、音乐之后 — 每天用的排在每周用的后面，肌肉记忆建立不起来 — 求片提到内容组第 2 位（媒体库之后），并挂待认领数角标。
- **[P1] 侧栏（Sidebar）· 上传分组** — 上传在「运营」组，与媒体库、求片分属两组 — 上传→入库→详情→播放是同一个流程的四步，被切成两个组，用户每次都要换组找下一步 — 上传移到内容组（建议改名「入库」），紧跟媒体库。
- **[P2] 内容分区（Sidebar `ZONES`）** — 只有电影/剧集两项，且和媒体库页签完全重复；`queries.ts` 的 `ZONES` 还定义了 `documentary`，两端都没用 — 多一行占位、少一层意义 — 合并进媒体库，或做成真正的分区管理。

### 2.2 逐页条目

**媒体库（LibraryView）**

- **[P0] 媒体库 · 工具条「新增入库」** — 主按钮没有 `onClick`，`router.tsx` 也没有 `/library/new` 路由 — 入库只剩「上传页按文件名自动识别」一条路；识别失败时界面只能「选已有影片」，无法新建，管理员被卡死（空态文案还写着「先从 TMDB 检索入库」，这条路并不存在） — 补「新建影片」流程：`videoApi.search`（TMDB/toDB 检索）→ 建记录 → 跳到上传。
- **[P1] 媒体库 · 表头「资源 / 求片 / 上映」** — 三个 `.th-sort` 都是纯装饰，无 `onClick`；而且 `videoApi.list` 本身不支持排序（只有 `videoApi.search` 支持 `sort_by`） — 20 条/页 × 209,486 部 = 10,475 页，想找「求片最多」或「最新上映」只能人工翻 — 二选一：列表切到 `videoApi.search` 接真排序，或去掉排序图标。
- **[P0] 媒体库 · 行尾「…」** — 按钮无 `onClick` — 所有行内操作（详情/删除/移动/复制播放地址）都没有落点，而详情页里这些操作又藏在「重命名」弹窗里 — 行内菜单：详情 / 复制播放地址 / 移动 / 删除 / 恢复。
- **[P1] 媒体库 · 全选框与行复选框** — 勾了没有批量操作条，且 checkbox 没有 `stopPropagation`，一点就整行跳详情 — 勾选功能实际不可用，还会误跳转 — 接批量（删除/移动/加入片单/导出）或删掉勾选列。
- **[P1] 媒体库 · 筛选条件** — 只有「全部/电影/剧集 + 片名」；接口还支持 `tmdb_id`、`todb_id`、`video_id`、`only_delete`、`with_media` — 管理员拿到 TMDB 链接、或投诉截图里的 `#12345`、或要找已删除影片，都没有入口 — 加「按 ID 搜索」与「只看已删除（回收站）」。
- **[P1] 媒体库 · 列表列** — 缺季集数（`parts_count` 未用）、缺「资源可用性」（只有数量，`with_media` 可拿）、缺成人标记（`video_is_adult`）、缺更新/入库时间 — 判断「这部能不能播 / 是不是成人片 / 最近谁动过」必须点进详情 — 加「季集 / 最近更新 / 成人」三列，资源列拆成「可用/总」。
- **[P2] 媒体库 · 导出** — `IconExport` 图标已备好但没有任何使用点 — 盘点、交接、给上游对账只能截图 — 当前筛选结果导出 CSV。

**影片详情（VideoDetailView）**

- **[P1] 影片详情 · 页头「删除」** — 与「同步」「返回列表」三个同权重 ghost 按钮并排，点击只有一个确认框 — 手滑概率高；删除是逻辑删除，而恢复入口不存在（见 2.3「回收站」），代价不可逆 — 删除收进「…」二级菜单，样式降为 danger，并要求输入片名确认。
- **[P0] 影片详情 · 资源行「…」** — 唯一动作是打开「重命名资源」弹窗；「复制播放地址」「同步元数据」「删除资源」全塞在这个弹窗底部 — 想验一下能不能播、想删错传的资源，都要先猜「改名」按钮；删除按钮还紧贴弹窗底部 — 拆成行内菜单，并单列一个「播放预览」（`mediaApi.playUrl` 其实已在用，只复制不播）。
- **[P1] 影片详情 · 资源表** — 只有 资源名/大小/上传者；`VideoMedia` 还有 `media_status`、`media_file_second`、`created_at`、`is_self_upload` — 「这片到底能不能播、多长、谁什么时候传的」都要再问人 — 补 状态、时长、上传时间 三列。
- **[P1] 影片详情 · 缺失操作** — `mediaApi.move`（资源移到正确季/集）、`mediaApi.restore`（恢复）、`mediaApi.listAll`（跨片看同一上传者的资源）、`uploadApi.saveSubtitle`（补字幕）全部无入口 — 传错集只能删掉重传，等于再扣一次胡萝卜 — 补「移动资源 / 恢复 / 上传字幕」。
- **[P1] 影片详情 · 季与集列表** — 每集只显示「N 资源 · M 字幕」，没有缺集视图，也不能批量看哪一集是空的 — 一部 40 集的剧要逐集点开确认 — 缺资源的集打红点，并给「只看缺集」开关。
- **[P2] 影片详情 · 元数据** — 只有全片 `videoApi.sync(todb_id)`，没有单集/海报的定向同步 — 海报缺一张也得等全量同步 — 提供同步范围选择。

**上传（UploadView）**

- **[P0] 上传 · 入库完成** — 成功只弹 toast + 队列行变绿，没有「查看详情」「继续给这部传字幕」「再传一集」 — 每天最高频的动作没有下一步，管理员只能回媒体库按片名重搜，重复 2~3 次点击 — `done` 行加「打开详情」，并支持「接续同一部影片继续入库」。
- **[P1] 上传 · 只支持视频** — `uploadApi.saveSubtitle`、`saveMusic`、`saveMusicHeadless`、`imageList`（图片库）、`videoBase`（先看已有资源避免重复）都无入口 — 字幕、音乐、封面图全部只能由客户端用户上传，管理员补不了；重复上传无法提前发现 — 上传页拆「视频 / 字幕 / 音乐 / 图片」四个页签，共用同一队列。
- **[P1] 上传 · 暂存区** — 每行只有一个 ⋮「归档」，而 `uploadApi.archive` 只传 `path_type + file_name`（不带目标影片）— 管理员不知道归档到哪部片、归档完在哪看 — 归档必须选目标影片/集，或明确写出落点。
- **[P1] 上传 · 识别失败后的选择器** — 只能按片名搜已有影片（`videoApi.search` 还支持 `type`/`sort_by`）— 同名电影/剧集极容易选错，且无法新建 — 选择器补 类型/年份/季集，并给「新建影片」出口。
- **[P2] 上传 · 权限与配额** — 不读 `session.is_can_upload` / `size_upload`，无权限账号会走到最后一步才失败 — 白传一个大文件，只看到后端报错 — 顶部显示配额，无权限时禁用入口。
- **[P2] 上传 · 分片上传** — `uploadApi.abort` 未接 — 传错大文件无法取消，只能等 — 上传中给「取消」。

**求片（SeekView）**

- **[P0] 求片 · 认领之后** — 认领成功只 toast，行内按钮变成「催片」；没有「去上传」、「标记完成」，也没有「取消认领」（`seekApi.claim` 的 `cancel` 未接） — 「求片 → 认领 → 入库」链路断在第一步之后；认领了但没传的求片会永远停在「已认领」 — 认领后给「去上传（预填片名）」，已认领给「取消认领」，传完给「标记完成」。
- **[P1] 求片 · 状态页签** — 只有 全部/求片中/已认领/已完成；`SeekStatus` 还有 `cancel`、`forget` — 用户取消或失效的求片完全查不到，无法回答「我的求片怎么没了」 — 补「已取消/已失效」（或合并为「已结束」）。
- **[P1] 求片 · 列表列** — 缺 `upload_expired_at`（认领到期时间）、缺求片人（`with_user` 参数未用）、缺悬赏流水（`seekApi.history` 未接） — 运营无法优先处理「快到期 + 悬赏高」的求片，只能按更新时间盲翻 — 加「到期倒计时」列，默认按到期时间 + 悬赏排序。
- **[P1] 求片 · 搜索与排序** — 无搜索框、无排序；接口支持 `video_title` 与 `sort_by(count_request|seek_carrot|upload_expired_at|updated_at)` — 待处理越积越多，只能一页页翻 — 加搜索框 + 排序下拉。
- **[P2] 求片 · 「每 30 秒刷新」** — 文案承诺自动刷新，但 `useSeekPage` 没有 `refetchInterval`（全仓只有 `usePlayingNow` 有轮询） — 管理员以为在看新数据，实际停在打开时那一刻 — 接轮询（`seekApi.poll` 已封装）或改文案。
- **[P2] 求片 · 详情** — `seekApi.query`、`seekApi.apply`（给影片打求片标记）无入口 — 无法回答「这条求片谁催的、催了几次、走没走过流程」 — 行点击开侧滑详情。

**片单（WatchlistsView / WatchlistDetailView）**

- **[P1] 片单 · 槽位显示** — `片单槽位剩余 {data ? Math.max(0, 2) : '—'}` 是硬编码 2 — 这个数字永远是错的，管理员会据此误判「还能不能新建」（真实值在 `session.slot_remaining` / `watchApi.slot`） — 接真实值，槽位为 0 时禁用「新建片单」。
- **[P1] 片单 · 无删除、无编辑** — `watchApi.remove`、`createOrUpdate({id})` 都未接 — 260 个片单改名、改公开状态、删掉废弃的，全都做不到，而片单槽位是稀缺资源 — 列表行菜单给 编辑/删除/排序，详情页头给「编辑」。
- **[P1] 片单 · 音乐片单没有落点** — 列表有「影视 / 音乐」分段，详情页却只查视频（`watchApi.music/searchMusic/addMusic/removeMusic` 全未接） — 点进音乐片单永远是「片单里还没有影片」，也无法加歌 — 详情页按 `type` 切换影视/音乐两种资源表。
- **[P2] 片单 · 维护者与订阅者** — `watchApi.maintainer`、`users` 无入口 — 无法把片单交给别人维护，也看不到谁在订阅 — 详情页加「维护者 / 订阅者」侧栏。
- **[P2] 片单 · 批量能力** — `updateVideos`（按 tmdb/toDB 批量加片）、`emptyVideos/emptyMusic`（清空）未接 — 建一个 50 部的片单要点 50 次「加入」 — 支持粘贴 ID 列表批量添加。
- **[P2] 片单 · 显示状态** — 列表只有「公开/私密」，缺 `user_is_show`（是否在客户端显示）和排序 — 「公开但不显示」这类异常状态查不出来 — 状态列拆成「可见性 / 显示 / 排序」。

**直播（LiveView）**

- **[P1] 直播 · 无编辑** — 只能新增/删除频道与源（`liveApi.save` 只服务新建，`updateMedia` 未接） — 改一个台的地址或名字只能删了重建，期间观看端 404 — 频道与源都可编辑，URL 旁给「测活」。
- **[P1] 直播 · 无搜索** — 77 个频道靠翻页（`liveApi.list` 支持 `code`/`title`） — 找地方台要翻 8 页 — 加搜索框。
- **[P2] 直播 · 列表列** — 缺「异常源数」（`LiveMedia.status` 只在展开后可见）、缺「正在观看人数」（`rankApi.playingLive` 未接） — 77 个台哪个死了、哪个热，得逐个展开 — 列表加这两列，异常的直接置顶。
- **[P2] 直播 · 排序** — 有 `sort` 列但无调整入口 — 客户端频道顺序无法调 — 行内上移/下移。

**线路（LinesView）**

- **[P1] 线路 · 无编辑** — `lineApi` 只有 create/remove，界面也只有增删 — 改一条线路地址必须删旧建新，期间所有走这条线的客户端（1,279 条线路的规模）直接断 — 至少做「新建替身 + 停用旧的」两步式替换，或推动后端加 update。
- **[P1] 线路 · 全量拉取 + 前端过滤** — `lineApi.list()` 一次拉 1,279 条再前端切片；`only_self` 参数未用 — 首屏和每次搜索都拉全量，慢链路上（本仓有「拉长缓存应对慢链路」的提交）明显卡 — 接 `only_self` 切换，推动后端分页。
- **[P2] 线路 · 列表列** — 缺 可用性 / 延迟 / 绑定客户端数 — 「这条线现在能不能用」无法回答 — 轻量健康探测 + 最近使用时间。

**商城（ShopView）**

- **[P1] 商城 · 商品无法删除** — `removeProduct`（`shopApi.deleteProduct`）在 `queries.ts` 里已封装，界面上没有任何按钮 — 卖错的商品只能永久挂在「已下架」，列表越积越脏 — 行内菜单给「删除」（带确认）。
- **[P1] 商城 · 无批量上下架** — 只能逐个 `toggleUp` — 一次活动上下架 20 个商品要点 20 次 — 加勾选 + 批量上/下架。
- **[P1] 商城 · 编辑弹窗字段不全** — 只能改 名称/售价/原价/库存/排序/分类/立即上架；`cover_url`（封面）、`description`、`exchange_way`、`user_buy_max`（限购）、`time_start/time_end`（活动时间）全缺 — 商品信息残缺，用户端展示不全，做限时活动做不了 — 弹窗补齐，或先 `shopApi.product` 拉全量详情再编辑。
- **[P1] 商城 · 列表无分类列、无搜索** — 只有 价格/库存/销量/状态（接口支持 `name`/`is_up`/`sort_by`） — 找「下架且库存为 0」的商品要翻页 — 加分类列 + 搜索 +「只看下架」。
- **[P2] 商城 · 分类无排序** — `sortCategory` 未接 — 客户端分类顺序固定 — 分类行加排序值或拖拽。

**订单（OrdersView）**

- **[P0] 订单 · 「删除订单」在「备注」弹窗里** — 备注是高频轻量动作，弹窗 footer 左侧却放了 danger 级「删除订单」（文案还写「不可撤销」） — 想改备注的人手滑删单，订单记录直接消失，对账时无法追溯 — 删除移到行内「…」菜单，备注弹窗只留「保存」。
- **[P1] 订单 · 发货无二次确认** — 点一下即发，页面无发货时间回显、无通知、无撤回 — 误发货只能线下解释；用户看到「已发货」但没收到 — 发货前确认（显示用户/商品/数量），发货后提供撤回或至少记录操作人。
- **[P1] 订单 · 列表列不足** — 缺 购买数量（`buy_number`）、单价、用户 ID、商户备注、发货时间 — 「这一单该不该发、发几件」都要截图问人 — 补 数量/用户/备注 列，行展开看明细。
- **[P1] 订单 · 无搜索、无详情** — 接口支持 `order_no`/`order_title`/`user_id`/`product_id`；`shopApi.product`、`ordersUser` 未接 — 用户报一个订单号，管理员只能翻页找 — 顶部订单号/用户名搜索，行点击开详情。
- **[P1] 订单 · 只有「发货」一条路** — 未支付订单没有「关闭订单」（`shopApi.closeOrder` 未接），没有退款入口 — 恶意占库存的未支付单只能等过期 — 未支付行给「关闭订单」，已支付行给「退款」入口。
- **[P2] 订单 · 视角单一** — 页头写「商户视角」，没有「全部/我的」切换 — 多商户运维时看不到别家订单 — 加视角切换。

**音乐（MusicView / SongDetailView）**

- **[P1] 音乐 · 无「无资源」筛选** — 只在 songs 页签用 `has_media===false` 打了个标，不能筛；`musicApi.songs` 支持 `has_media` — 523,369 首里要补资源只能一首首翻，这是音乐域唯一每天有价值的动作却做不了 — 加「只看无资源」开关（配套 `batchHashExist` 去重）。
- **[P1] 音乐 · 专辑/歌手行不可点** — `onClick={() => isSong && navigate(...)}`，专辑和歌手行没有详情 — 无法从歌追到专辑，也无法维护歌手信息（`syncSpotifyArtist` 已封装） — 补专辑/歌手详情页。
- **[P1] 音乐 · 歌曲详情只能看不能改** — 歌词只读（`createLyric`/`deleteLyric` 未接）、资源不可删/移/试听（`deleteMedia`/`moveMedia`/`playUrl` 未接） — 歌词错字、资源传错都只能等客户端用户来修 — 补歌词编辑与资源管理。
- **[P2] 音乐 · 行内「…」只做同步** — 没有删除、没有「加入片单」 — 删一首歌必须点进详情 — 行内菜单补 删除/加入片单。

**账号（AccountView）**

- **[P0] 账号 · 只有「我」** — 全站没有 `/users/:id`：订单里的用户名、求片里的认领人、封禁列表、邀请列表、胡萝卜流水里的 `user_id` 全都不可点；`payApi.userInfo/userCarrot/userSign`、`carrotApi.history(user_id)`、`mediaApi.listAll(user_id)` 全部空置 — 客服场景（「充值没到账」「我被误封了」「有人登我号」）从任何列表都进不到用户，只能去后端捞数据 — 新建「用户」页：按 用户ID/用户名/Telegram 查 → 资产（胡萝卜/签到/邀请树/封禁/设备/上传记录）。
- **[P0] 账号 · 封禁只有「解除」没有「封禁」** — `banApi.change` 只在前端用 `enable`，没有 `disable` + 原因输入 — 后台封不了人，遇到违规用户只能走别的渠道 — 封禁页加「新增封禁（用户 ID + 原因 + 是否连带邀请人）」。
- **[P1] 账号 · 设备管理缺失** — `userApi.videoHistory`、`videoLogout` 未接 — 「我被别人登着」这类工单无法处理 — 用户页加设备列表 +「踢出」。
- **[P1] 账号 · 邀请记录无搜索无分页** — `inviteApi.history` 支持 `username/user_id/telegram_user_id` + 分页，界面固定第 1 页、10 条 — 邀请多的人看不到后面的下级，也无法按 ID 找人 — 加搜索框与分页。
- **[P2] 账号 · 邀请备注改不了** — `inviteApi.remark` 未接 — 备注只能建时填 — 记录行加「编辑备注」。
- **[P2] 账号 · 胡萝卜历史翻页无上界** — 下一页按钮没有 `disabled`，末页之后可以无限点出空表 — 加 `Pager` 统一（其他页都用 `Pager`，这里手写了分页）。

**支付（PayView）**

- **[P1] 支付 · 只有查单 + 转赠** — `payApi.create`、`close`、`testNotify`、`apply`、`update`、`notifyEmail`、`userCarrot`、`userInfo`、`userSign` 全部空置 — 这是一个「配置页」而不是「运营页」：补单、关单、发通知、查用户余额都做不了 — 拆三块：配置（申请/更新/回调）/ 订单（查/关/测试回调）/ 通知（发邮件）。
- **[P1] 支付 · 转赠重复且走错通道** — 账号页和支付页各有一份「转赠胡萝卜」，都调 `carrotApi.transfer`，而支付域的 `payApi.transfer` 未接 — 同一动作两个入口、两个后端语义，账对不上时无法判断走了哪条 — 只保留一处（用户页），并明确通道。
- **[P2] 支付 · 404 时整页隐藏** — 连与支付无关的转赠也一起被 `display:none` — 没开支付的实例上，转赠入口「消失」 — 转赠移出支付页。

**概览（OverviewView）**

- **[P0] 概览 · 没有待办区** — 见 1.3 第一条。
- **[P1] 概览 · 所有卡片都不可点** — 片库总量、待处理求片、上传榜行、正在播放行都没有链接 — 看到数字后要自己再找一次入口，等于首页只提供信息不提供行动 — 每张卡/每行都链到对应列表（带筛选与搜索词）。
- **[P1] 概览 · 缺运营侧指标** — 今日上传量、上传失败数、待发货订单、待审核/被驳回店铺、异常直播源、无资源音乐数 —— 一个都没有 — 「今天要不要动手」无从判断 — 概览拆「待办 / 今日 / 存量」三段（见第七节表 B）。
- **[P2] 概览 · 标题与数据不符** — 标题是 `${month} 月`，数据是总量（没有任何时间范围） — 会让人误读为月度数据 — 加时间筛选，或标题改成「总览」。
- **[P2] 概览 · 正在播放只显示 3 条且不可点** — 看不到谁在看、不能跳片 — 给「查看全部」与行链接。

**侧栏（Sidebar）**

- **[P0] 侧栏 · 全局搜索框是死的** — placeholder 写「搜索片名、用户名或编码」，右侧还挂着 `⌘K` 徽标，但 `<input>` 没有 `onChange`/`onKeyDown`，全仓也没有 `⌘K` 监听 — 209,486 部片 + 523,369 首歌 + 全站用户，管理员最需要的全局检索不存在；找一部片要先想「它属于哪个列表、用什么词」 — 接全局搜索（片名 / 用户 / 影片 ID / 订单号同框），`⌘K` 聚焦，结果直跳详情。
- **[P2] 侧栏 · 收起按钮无行为** — `aria-label="收起侧栏"` 但没有 `onClick`，`components.css` 里已经写好了窄栏断点 — 点了没反应 — 接折叠状态并用 localStorage 记忆。
- **[P2] 侧栏 · 角标位空置** — `NavItem.tail` 已实现渲染，但没有任何一项赋值 — 求片待处理、待发货、待审店铺的数量无法一眼看到 — 概览/求片/订单挂数字角标。
- **[P2] 侧栏 · 「片单」带 chevron 却不可展开** — `chev: true` 只是个箭头图标 — 会让人以为点不开是 bug — 要么去掉，要么真做二级（我创建的 / 我订阅的 / 音乐）。

### 2.3 特别条目：回收站（承诺了但不存在）

- **[P0] 影片详情 / 资源删除 · 确认框文案** — 两处 hint 都写「可从回收处恢复」，全站没有回收站：`mediaApi.restore`、`mediaApi.listAll(only_delete)` 已封装但无入口；影片本身（`videoApi.remove`）连恢复端点都没有 — 管理员相信文案去删，删完发现无处恢复；资源重传还要再扣一次胡萝卜 — 二选一：把 `listAll(only_delete:true)` + `restore` 做成「回收站」页（资源级），或把文案改成「不可恢复」，影片级删除改成更重的确认。

## 三、页面信息是否足够做决定

判断标准：**列表页能不能直接做决定，而不点进详情**。

| 页面 | 缺失字段 | 缺了会怎样（必须点进详情/必须问人） |
|---|---|---|
| 媒体库 | 季集数、最近更新时间、成人标记、资源可用性（拆可用/总）、入库人 | 判断「这部能不能播 / 缺几集 / 是谁传的」都要进详情；209,486 部里无法用眼睛扫出异常 |
| 影片详情·资源表 | `media_status`、`media_file_second`、`created_at`、`is_self_upload` | 判断「这个资源还能不能播、多长、谁什么时候传的」都要再问 |
| 影片详情·季与集 | 缺集标记、季度汇总 | 40 集的剧要逐集点开找空集 |
| 求片 | `upload_expired_at`（到期）、求片人、悬赏流水数 | 无法排优先级，无法回答「谁在催」，也只能按更新时间翻 |
| 片单列表 | `user_is_show`（是否显示）、维护者数、排序值 | 「公开但不显示」的异常查不出来；排序问题查不出来 |
| 商品 | 分类名、限购、活动时间窗、封面是否缺失 | 判断「这个商品为什么不能买」要进编辑弹窗逐项看 |
| 订单 | `buy_number`、单价、用户 ID、商户备注、发货时间 | 「发几件、发给谁、备注要求什么」都得截图问人 → 直接导致发错货 |
| 直播 | 异常源数、正在观看人数、更新时间（有） | 77 个台哪个死了得逐个展开 |
| 线路 | 可用性、延迟、绑定客户端数 | 「这条线现在能不能用」无法回答 |
| 音乐 | `count_medias`、是否有歌词、播放量 | 无法定位「有歌无资源」「有歌无词」 |
| 账号·邀请记录 | 无搜索、无分页 | 下级超过 10 人后完全看不到 |

补充两条**跨页字段一致性**问题：

- **[P1] 订单 / 求片 / 邀请 / 胡萝卜 · 用户名** — 四处都渲染了 `username`/`upload_username`，但都不是链接、也没有 `user_id` 可见 — 想拿用户名去别处核对「是不是同一个人」做不到（管理员会拿昵称猜） — 用户名一律渲染成「昵称（ID 后 6 位）」，并链到用户页。
- **[P2] 媒体库 / 详情 · ID 体系** — 列表显示 `#video_id · todb N`，详情显示 `#video_id / toDB / TMDB`，求片显示 `item_id · todb`，位置不统一 — 用户报「编号 12345」时，管理员无法立刻判断这是 video_id 还是 todb_id — 全站统一「video_id / toDB / TMDB」三个标签的固定顺序，并提供按任一 ID 搜索。

## 四、导航结构

- **[P1] 导航 · 分组语义** — 「内容 / 运营 / 系统」三组本身合理，但成员放错：上传（内容生产）在运营组、概览（首页）塞进内容组、支付（配置）在系统组、用户（缺失）没有组 — 见第七节表 A 的重排。
- **[P1] 导航 · 「上传」应该提到内容组** — 应该。上传 → 入库 → 详情 → 播放是同一流程的四步，现在被切成两个组；而且上传不在首页任何位置。建议移到内容组，紧跟媒体库，并改名「入库」（组内其他项都是名词，唯独它是动词，语义也不齐）。
- **[P1] 导航 · 「支付」放在系统组** — 位置基本对（偶尔用、配置类），但名字不对：对管理员它是「收款与对账」，且页面里混入了转赠（属于账号/用户域）。建议改名「财务」，只留 配置 / 对账 / 通知，转赠挪到用户侧。
- **[P1] 导航 · 缺「用户」组** — 目前「账号」= 我自己，用户维度整个缺失（见 2.2 账号条） — 新增「用户」组：用户查询 / 封禁 / 邀请，把账号页的「封禁」页签搬过去（封禁是对别人的操作，不该在「我的账号」里）。
- **[P2] 导航 · 概览不应该属于「内容」组** — 它是全局首页，被放在内容组第一位会让「内容」组语义模糊（概览不是内容） — 概览独立置顶，不属于任何组。
- **[P2] 导航 · 组内顺序未按频率排** — 内容组：概览/媒体库/片单/求片/音乐（求片第 4）、运营组：上传/直播/商城/订单（订单第 4） — 高频项排在后 — 每组内按「每天 → 每周 → 偶尔」降序（表 A 给了具体顺序）。

## 五、危险操作的位置

两类错位同时存在：**该重的太轻**、**该远的太近**。

- **[P0] 订单 · 删除订单在「备注」弹窗** — 见 2.2 订单第一条（本审查最危险的一处：高频轻量弹窗内嵌不可逆删除）。
- **[P1] 影片详情 · 页头三按钮等权重** — 「删除 / 同步 / 返回列表」全是 `btn btn--ghost`，删除没有 danger 样式 — 手滑点错就是下架一部片（且恢复入口不存在） — 删除降级进「…」菜单 + danger 样式 + 输入片名确认。
- **[P1] 影片详情 · 删除资源/删除字幕藏在「重命名」弹窗底部** — 想改名的人看到底部一个 danger 按钮 — 误删资源会扣胡萝卜 — 删除独立成行内菜单项，不与改名同处。
- **[P1] 歌曲详情 · 删除与收藏、返回列表并排** — 三个同级 ghost 按钮 — 误删歌曲 — 同上，收进「…」菜单。
- **[P1] 直播 · 删除频道按钮紧贴「点击整行展开」热区** — 已有 `stopPropagation`，但视觉上仍贴在同一行右端 — 展开频道时手滑删掉整个频道（连带所有源） — 删除移到展开面板内，或行内「…」菜单。
- **[P1] 转赠胡萝卜 · 无二次确认、无收款人核对** — 账号页有弹窗但点「转赠」直接提交；支付页完全内联直接提交；两处都只校验「ID 非空 + 金额范围」，不显示对方昵称 — 输错一个字符就把钱转给陌生人，且不可撤回 — 提交后弹出「转给 {昵称} {金额}」的二次确认，并显示对方 ID 后 4 位。
- **[P1] 行内 ghost 危险按钮过多** — 撤销邀请、解除封禁、删除分类、删除线路、移出影片、删除直播源，六处都是同一个 `btn btn--quiet` 幽灵按钮 — 没有视觉分级，操作员对「危险」脱敏 — 统一 danger 变体 + 「…」菜单承载。
- **[P2] 所有确认框按 Enter 即确认** — `ConfirmHost` 里 `Enter → settle(true)`，且确认按钮 `autoFocus` — 连按 Enter 时会穿过确认框（例如连续改名时） — 危险类确认框禁用 Enter 快捷，只接受点击。
- **[P2] 删除类文案不一致** — 影片说「可从回收处恢复」，资源说「会扣除胡萝卜，可从回收处恢复」，字幕说「会扣除 1 个胡萝卜，可重新上传」，歌曲说「资源不会被立即清除」 — 操作员无法预期后果 — 统一「是否可恢复 / 是否扣胡萝卜 / 影响范围」三行固定结构。

## 六、流程断点

### 链路 A：上传 → 入库 → 详情 → 播放

| 步 | 动作 | 下一步该去哪 | 界面给了出口吗 |
|---|---|---|---|
| 1 | 拖文件进上传页 | 等自动识别 | ✅ 状态机自动 |
| 2 | 识别失败 | 选目标影片 | ⚠️ 只能选已有；**无法新建影片**（P0） |
| 3 | 上传中 | 等待 | ⚠️ 有进度条，**无取消**（P2） |
| 4 | 入库完成 | 打开详情 / 补字幕 / 再传一集 | ❌ **只弹 toast，无出口**（P0） |
| 5 | 影片详情 | 确认资源挂在哪一集 | ⚠️ 资源表无状态列、无「移动资源」（P1） |
| 6 | 播放验证 | 点一下看能不能播 | ❌ 只有「复制播放地址」（还藏在重命名弹窗里），无播放预览（P1） |
| 7 | 回列表 | 回到刚才的筛选结果 | ❌ 「返回列表」硬编码 `page=1&q=''&type=''`，筛选与页码全丢（P1） |

- **[P0] 链路 A · 第 4 步** — 见 2.2 上传第一条。
- **[P1] 链路 A · 第 7 步（VideoDetailView 页头「返回列表」）** — `<Link to="/library" search={{page:1,page_size:20,q:'',type:''}}>` 把上下文写死 — 从第 380 页点进详情再返回，回到第 1 页、筛选清空，重新找一遍 — 用 `router.history.back()` 或把来源 search 作为 `from` 参数带过去。

### 链路 B：求片 → 认领 → 入库

| 步 | 动作 | 下一步该去哪 | 界面给了出口吗 |
|---|---|---|---|
| 1 | 用户发起求片 | 管理员感知 | ⚠️ 概览只有不可点的数字（P0）；求片页不自动刷新（P2） |
| 2 | 认领 | 去上传页传这部片 | ❌ **无出口**（P0） |
| 3 | 上传入库 | 带 seek 上下文（片名/季集预填） | ❌ 上传页不接收任何 seek 参数（P1） |
| 4 | 传完 | 标记求片完成、结算悬赏 | ❌ **无入口**（P0）；`seekApi.claim` 的 cancel 也没接 |
| 5 | 通知求片人 | 站内/邮件 | ❌ 无入口（`payApi.notifyEmail` 未接） |

- **[P0] 链路 B · 第 2/4 步** — 见 2.2 求片第一条。
- **[P1] 链路 B · 第 3 步** — 上传页与求片页没有任何参数传递 — 认领后要手动记住片名，再到上传页等识别（识别又可能失败） — 上传页支持 `?seek_id=&title=` 预填并回填认领状态。

### 链路 C：商品 → 订单 → 发货

| 步 | 动作 | 下一步该去哪 | 界面给了出口吗 |
|---|---|---|---|
| 1 | 新增商品 | 补封面/描述/兑换方式/限购/时间窗 | ❌ 弹窗缺这 5 类字段（P1） |
| 2 | 上架 | 批量上架 | ⚠️ 只能逐个 toggle（P1） |
| 3 | 用户下单 | 看这个商品的订单 | ❌ 商品页无「查看该商品订单」，订单页无商品链接（P1） |
| 4 | 待发货 | 概览/侧栏的待发货数 | ❌ 概览没有该指标（P0） |
| 5 | 发货 | 确认 + 通知用户 | ⚠️ 点即发、无确认、无通知（P1） |
| 6 | 售后 | 退款 / 关单 / 查用户 | ❌ `closeOrder`、退款、用户页全缺（P1/P0） |

- **[P1] 链路 C · 第 3 步** — 商城与订单是两个孤立页面，没有互相链接 — 用户投诉「这个商品少了」时，管理员要在订单页用订单号反查，而订单页没有搜索框（P1） — 商品行加「该商品订单 N 单」直链 `?product_id=`；订单行加商品链接。
- **[P1] 链路 C · 第 6 步** — 发货后没有任何后续动作，退款/关注单/通知全部缺失 — 售后只能在线下处理 — 已发货行给「退款 / 关注单」，未支付行给「关闭订单」。

## 七、主次重构建议

### 表 A：导航怎么排

原则：**按频率排组内顺序；按「同一条流程」排同组；首页独立置顶；每组都挂待处理角标。**

| 位置 | 项 | 角标 | 频次 | 相对现在 |
|---|---|---|---|---|
| 顶部（不属于任何组） | **概览** | 待办总数 | 每天 | 从「内容」组第一项提为独立置顶 |
| 内容（生产） | **媒体库** | — | 每天 | 原位 |
| 内容 | **求片** | 待认领数（`default`） | 每天 | 从第 4 位提到第 2 位 + 角标 |
| 内容 | **入库**（原「上传」） | 待上传/失败数 | 每天 | 从「运营」组移入，改名「入库」，跟媒体库相邻 |
| 内容 | **片单** | — | 每周 | 原位（去掉假 chevron 或做真二级） |
| 内容 | **音乐** | 无资源歌曲数 | 每周 | 原位 |
| 运营 | **订单** | 待发货数 | 每天 | 从第 4 位提到第 1 位 + 角标 |
| 运营 | **商城** | 待审核/被驳回 | 每周 | 原位 |
| 运营 | **直播** | 异常源数 | 每周 | 原位 |
| 用户（新增组） | **用户查询** | — | 每天 | 新增（`/users/:id`） |
| 用户 | **封禁** | 封禁数 | 每周 | 从账号页「封禁」页签搬来 |
| 用户 | **邀请** | — | 偶尔 | 从账号页「邀请」页签搬来 |
| 系统 | **线路** | 异常数 | 每周 | 原位 |
| 系统 | **财务**（原「支付」） | — | 偶尔 | 改名，移出转赠，只留 配置/对账/通知 |
| 系统 | **账号** | — | 偶尔 | 只留 资料 / 胡萝卜 / 安全+设备 |

配一条强约束：**侧栏搜索框（⌘K）必须先做**。它把「按列表找」变成「按东西找」，是上面所有「入口分散」问题的最小成本补偿 —— 一个输入框吃掉 5 个页面的检索入口。

### 表 B：首页（概览）怎么排

原则：第一屏只放「需要我动手的事」；存量数字放第三段；每一条都可点、都带数量。

| 区块 | 内容 | 数据来源 | 解决什么 |
|---|---|---|---|
| **① 待办清单**（第一屏，占 2/3 宽） | · 待认领求片 N（并显示最快到期）<br>· 待发货订单 N（并显示被催单数）<br>· 上传失败 / 待处理 N<br>· 待审核店铺 N<br>· 异常直播源 N<br>· 疑似无资源影片抽查 | `seekApi.list(status:default)`、`shopApi.ordersShop(is_delivery:false)`、上传队列、`shopApi.sellerBase`、`liveApi.media` | 每天上班第一眼就知道要做什么，替代「挨个页面翻」 |
| **② 今日**（右侧 1/3） | 今日上传数 / 入库资源数 / 新增求片 / 成交单数与金额 / 正在播放设备数 | `rankApi.upload`、`recordApi`、`rankApi.playingVideo`、`payApi.base` | 一眼判断「今天是否正常」 |
| **③ 快捷动作**（右侧 1/3） | 上传文件 / 新建片单 / 新建商品 / 新增线路 | 直接跳目标页并打开对应弹窗 | 少两次点击 |
| **④ 存量健康**（第二屏） | 片库总量（可下钻电影/剧集）、音乐总量与无资源数、直播频道与异常源、线路总数与异常数 | `videoApi.list`、`musicApi.songs(has_media:false)`、`liveApi.library`、`lineApi.list` | 周会/体检用，替代现在第一屏的「分区构成」 |
| **⑤ 近期动态**（第二屏） | 上传榜（可点上传者）、正在播放（可点进影片）、最近入库 | `rankApi.upload`、`rankApi.playingVideo` | 保留现有价值内容，但补上链接 |

三条执行顺序建议（收益/成本比从高到低）：

1. **先补「断头路」**（1 天级）：侧栏全局搜索、上传完成 → 打开详情、求片认领 → 去上传、发货二次确认、「返回列表」保留筛选、片单槽位真值、删除订单挪出备注弹窗。这七处不改任何后端契约，只改 `views/` + 少量 `queries.ts`。
2. **再补「用户 + 回收站」两个缺失域**（2~3 天级）：`/users/:id`（复用 `payApi.userInfo/userCarrot/userSign` + `carrotApi.history(user_id)` + `mediaApi.listAll(user_id)` + `userApi.videoHistory`）、`/recycle`（`mediaApi.listAll(only_delete)` + `mediaApi.restore`）。这两块是客服与误删的根因。
3. **最后重排首页与导航**（1 天级，纯前端）：按表 A / 表 B 落地，角标依赖 ① 里那几个 count 查询（`useSeekOpen` 已经是这个模式，复制即可）。
