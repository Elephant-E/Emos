## 结论先行

1. **上轮 16 条 P0 去重为 12 个问题：1 条彻底解决、2 条解决但带出新问题、7 条部分解决、2 条未解决；56 条 P1 只解决了 5 条。** 解决得最干净的是「封禁入口」「媒体库排序假表头」「商品删除」「槽位真值」；做得最敷衍的是「认领后出口」——给了两个 `<a href>` 裸锚点，整页刷新、不带上下文、也没有收口动作。规律很清楚：**换一个按钮、接一个接口的都做了；加一列、加一个筛选、加一个页面的都还欠着。**
2. **首页从「存量报表」换成了「个人仪表盘」，方向对了一半。** 作为个人页成立；作为管理台首屏仍不成立：首屏四格全是「我的资产/我的微动作」，没有一格回答「今天有什么要我处理」。更关键的是 —— **承载待办的数据层已经写好（`useTodos()` 会拉待认领求片 / 待发货订单 / 封禁数，且对普通用户返回 null），但全站没有一处引用它**。这是本轮最可惜的一处「建好了没接上」。
3. **回收站上线，但踩了 362 万条的现实。** 没有搜索、没有筛选、没有上传者，只能翻页（20/页 = 18 万页）；`mediaApi.listAll` 的 `media_id`/`user_id`/`status` 三个过滤参数一个都没用。凡是「我不小心删了某个资源」的场景，实际上仍然不可完成。
4. **客服链路是「半条」。** `/users/:id` 能从订单、邀请记录、封禁列表点进去（3 个入口），但：没有「按用户 ID / 用户名查人」的入口（客服拿到的输入恰恰是 ID）；进去之后没有返回来源；用户页只有封禁状态可用，胡萝卜卡是写死的「—」（而 `payApi.userCarrot` 已封装未用），没有订单、求片、上传、设备。更讽刺的是用户页里那句「申请成为服务商后可看全」指向 `/pay`，而 `/pay` 上根本没有申请按钮（`payApi.apply` 未接）。
5. **危险操作从一个极端滑到另一个极端。** 上轮「删除订单藏在备注弹窗」已修，但订单、商品、片单、直播源、线路现在都是**每行常驻一个无样式的「删除」**，与「备注」「编辑」「上架」同级。既没有 danger 分级，也没有菜单收纳。
6. **导航项数其实没过载（实测 5 / 4 / 4 + 2），但分布仍是错的**：概览塞在「内容」、回收站塞在「系统」、`/users/:id` 根本没有侧栏入口、内容分区两行与媒体库页签完全重复。

## 三、这一版概览作为「仪表盘」成立吗

**结论：作为个人页成立，作为管理台首屏不成立。** 差的不是设计，是一条「待办」层。

### 3.1 成立的部分

- 信息有主次：4 张状态卡（签到 → 胡萝卜 → 槽位 → 上传）是有顺序的，签到卡带动作、槽位/上传卡可点，符合「先能动手、再看数字」。
- 「继续观看」「我的片单」「快捷入口」都是可点的真链接，不再是上轮那种「卡片好看但不可点」。
- 「我的近况」用了真实数据（`useWatchStats` → `stats/video/history`），微条 + 胡萝卜流水双层信息，密度合适。
- 不按身份分支这个决定本身是对的：它不是「管理员首页」或「用户首页」，而是「同一个人的首页」。

### 3.2 不成立的部分（按严重度）

- **[P0] 概览 · 首屏没有待办，而数据层已经有了** — 首屏四格分别是 签到 / 胡萝卜 / 我的上传 / 片单槽位，全是「我的资产 + 我的微动作」，没有一格回答「今天有什么要处理」。`useTodos()` 已经把待认领求片数、待发货订单数、封禁数都拉好了（并且用 `safe()` 把失败项降级为 null，对无权限的普通用户天然安全），却没有任何页面引用 — 管理员每天的第一诉求仍然无处落地：要么去求片页翻、要么去订单页筛、要么漏掉 — 在签到卡上方加一条「待办条」：`待认领求片 12 · 待发货 3 · 封禁 7`，每项是链接，全部为 0 时整条不渲染。这样不需要身份分支，普通用户看到的还是现在这一版。
- **[P0] 概览 · 「签到」占了首屏最贵的一格** — 签到一天只能点一次，点完立即退化成只读数字，却和一个 365 天都有效的入口并列第一排 — 首屏的黄金位置被一次性动作占用 — 签到降级成问候语右侧的行内小按钮（`早上好，XX  [立即签到 +5]`），把四格让给 待办 / 槽位 / 上传 / 最近入库。
- **[P1] 概览 · 缺「最近入库 / 我最近上传」** — 上传者和管理员最常回看的是「我刚传的那部挂对集了吗」，现在要走 上传→(无记录)→媒体库→搜片名 三步 — 仪表盘漏掉了自己最高频的确认动作 — 加一张「最近入库」卡（`mediaApi.listAll(user_id=我, 按时间倒序)`，或直接从上传队列的本地历史取），每行可点进详情。
- **[P1] 概览 · 「继续观看」的每一条都点不进去** — 行是纯 `<li>`，没有 `Link` — 看到「看到 43% 的那部」却无法一键继续，只能自己去媒体库搜 — 行整块包 `Link` 到 `/media/$videoId?season=&episode=`。
- **[P1] 概览 · 「我的近况」没有错误态** — `stats` 失败时 `stats.data` 恒为 undefined，页面永远停在骨架屏（该接口在真机实测约 11 秒，超时概率不低）— 用户会以为页面卡死 — 补 `stats.isError` 分支与重试。
- **[P2] 概览 · 「片单槽位」卡文案与落点不符** — 卡上写「可用胡萝卜兑换」，点击却跳到片单列表（兑换按钮在账号页「资料」tab）— 想兑换的人落到了错的地方 — 落点改 `/account?tab=profile`，或卡上直接给「去兑换」。
- **[P2] 概览 · 第二屏碎片化** — 结构是 4 + 2 + 2 共 8 张卡，每张只承载 1~2 条信息，滚动一次看到的信息量偏低 — 近况与片单可以合并成一张「我的」卡（左近况右片单），把第二屏让给「最近入库」。
- **[P2] 概览 · 死代码** — `useSeekOpen`、`useZoneCounts`、`useRankUpload`、`usePlayingNow`、`useMyWatchlists`、`useIsAdmin` 六个 hook 与 `isMerchant` 能力字段重写后已无引用 — 留存会让人误以为概览还有这些数据 — 要么接回（播放中/上传榜对管理员有价值），要么删。

## 四、新增与改动的页面有没有形成闭环

### 4.1 `/users/:id`（客服链路）—— **进得去，出不来，且没有「找」的入口**

| 方向 | 现状 |
|---|---|
| 从订单进入 | ✅ 有（`order.user.user_id` 存在时渲染成链接） |
| 从封禁列表进入 | ✅ 有（[`AccountView.tsx`](src/views/AccountView.tsx#L448)） |
| 从邀请记录进入 | ✅ 有 |
| 从求片进入 | ❌ 认领人 `upload_username` 仍是纯文本 |
| 从胡萝卜流水进入 | ❌ 该表没有用户列 |
| **按 ID / 用户名找人** | ❌ **没有任何入口**（侧栏搜索只搜片名；没有用户列表页） |
| 返回来源 | ❌ 页面只有「封禁列表」「邀请记录」两个固定跳转，回不到订单/求片；也没有面包屑上级链接 |

- **[P0] 用户 · 没有「查用户」入口，客服链路从第一步就断** — 客服工单给的是「用户 ID `e…s`」或「用户名 xxx」，而界面只能从已有的订单/邀请/封禁行里反查 — 遇到「我充值没到账，我的 ID 是 …」这种最常见的话术，管理员没有任何地方能输入它 — 侧栏搜索框支持三种前缀（`e…s`/`@用户名`/片名）分别跳 用户/用户/媒体库，或单独加一个 `/users` 列表页（唯一可行的数据源是 `inviteApi.history(username)` 与 `payApi.userInfo(username)`）。
- **[P1] 用户 · 胡萝卜卡是写死的「—」** — 卡片文案固定「— 需要服务商权限」，即使当前账号有权限也永远不显示余额，而 `payApi.userCarrot` 已封装未用 — 客服无法回答「我余额多少」，用户页最有价值的一格是空的 — 接 `payApi.userCarrot`；无权限时才显示「—」+ 提示。
- **[P1] 用户 · 只有「封禁状态」可用，其余三块缺失** — 页面 = 4 张卡（状态/胡萝卜/上传量/邀请）+ 2 张表（资料/最近活跃）。没有 **订单**、没有 **求片**、没有 **上传的影片**、没有 **设备**、没有 **胡萝卜流水** — 客服 4 类问题里只能答「封禁」这一类 — 按「资产 / 行为 / 关系 / 风险」四段组织：资产（胡萝卜+流水）、行为（订单/求片/上传）、关系（邀请树）、风险（封禁/设备）。
- **[P1] 用户 · 没有返回来源的路径** — 从订单点进来后，只能跳去「封禁列表」或「邀请记录」，或手动改 URL — 处理完一个用户要重新找一遍订单 — 页头加「返回上一页」（router history back），并把两个固定跳转改成来源相关。
- **[P2] 用户 · 封禁原因硬编码** — `reason: '后台手动封禁'` 写死在代码里，没有输入框 — 三个月后回看封禁列表，全是同一句话，等于没有原因 — 弹窗补一个原因输入（可选），默认值保留。
- **[P2] 用户 · 小瑕疵** — `String(invited?.username ?? '') ?? ''` 是死代码；`limited` 只加了一行提示，四张卡仍照常渲染（其中三张是「—」） — 无权限时页面看起来像坏了 — 无权限时把不可用的卡直接换成一条说明。

### 4.2 `/recycle`（回收站）—— **能恢复，但找不到要恢复的东西**

| 方向 | 现状 |
|---|---|
| 从侧栏进入 | ✅ |
| 从详情页「删除后」进入 | ❌ 删除后只 toast；详情若已删则显示「找不到这部影片（去回收站看看）」—— 但那个空态只有一个「回到媒体库」按钮，**没有回收站链接** |
| 从媒体库进入 | ❌ 媒体库无回收站入口 |
| 恢复后回到原片 | ❌ 只能回媒体库搜片名 |
| 在 362 万条里定位一条 | ❌ 无搜索、无筛选、无上传者列 |

- **[P0] 回收站 · 362 万条没有搜索** — 只有「资源 / 影片」两个 tab 与翻页，`mediaApi.listAll` 的 `media_id`/`user_id`/`status` 参数一个没用 — 「我不小心删了《X》的资源」这个场景实际不可完成（18 万页） — 顶部加：按 资源 ID / 上传者 ID / 片名 搜索 + 「只看近 7 天」。
- **[P1] 回收站 · 「恢复影片」复用了删除接口** — `restoreVideo` 实际调用 `videoApi.remove(videoId)`，即 `PUT /api/video/{id}/delete`，且忽略了响应里的 `is_delete` — 若后端不是 toggle 语义，点「恢复」等于再删一次；即使是 toggle，UI 也无从判断成功与否，一律 toast「已恢复」 — 后端补 `/api/video/{id}/restore`；过渡期至少读回 `is_delete`，只有置为 false 才提示成功。
- **[P1] 回收站 · 恢复资源不显示胡萝卜消耗** — `mediaApi.restore` 返回 `{carrot:-10}`（`docs/api-shapes.md` 明确），UI 的确认框写「可能消耗胡萝卜，具体以后端返回为准」，成功后只 toast「已恢复」 — 用户不知道扣了多少，会当成 bug 来问 — toast 直接显示 `已恢复，-10 胡萝卜`（`mediaApi.remove` 在详情页就是这么做的，这里是漏了）。
- **[P1] 回收站 · 与详情页的互链是断的** — 删完不回链接、删后的空态也不给链接、恢复后不跳回原片 — 三处都指向「没有出口」 — 详情页删除成功后 toast 里带「去回收站」；「找不到这部影片」空态加回收站按钮；恢复成功后行内变「已恢复 · 查看影片」。
- **[P2] 回收站 · 列表列不足** — 资源 tab 缺「上传者」（`user_pseudonym` 已在返回里）与「删除人」；影片 tab 缺「删除时间」 — 管理员无法判断「谁删的、什么时候删的」，而这正是追责/恢复的依据 — 补 上传者 / 删除时间 两列。

### 4.3 `/music` + `/music/song/:id`（上一轮就存在，本轮复核）

- **[P1] 音乐 · 详情页仍是只读** — 歌词不可编辑（`createLyric/deleteLyric` 未接）、资源不可删/移/试听（`deleteMedia/moveMedia/playUrl` 未接） — 52 万首歌的一首歌词错了，管理员只能等客户端用户改 — 至少给「歌词编辑」与「资源删除」两个动作。
- **[P1] 音乐 · 专辑/歌手仍是死行** — `onClick={() => isSong && navigate(...)}` — 点专辑、点歌手都没有反应，用户会以为页面坏了 — 补专辑/歌手详情，或把行改成不可点样式（不要 `cursor: default` 之外还保留整行高亮）。
- **[P1] 音乐 · 无「无资源」筛选** — 列表只有 badge，不能筛；`musicApi.songs` 支持 `has_media` — 补资源的唯一入口没有落点 — 加「只看无资源」开关。

### 4.4 `/pay`（支付 / 服务商）—— **引导进来，但这里没有下一步**

| 方向 | 现状 |
|---|---|
| 从侧栏进入 | ✅「系统 → 支付」 |
| 从用户详情「申请成为服务商」进入 | ✅ 有链接 → `/pay`；❌ 但 `/pay` 上没有申请入口 |
| 从订单/退款进入 | ❌ 无 |
| 404（未开通支付模块）时 | ⚠️ 整页 `display:none`，连与支付无关的「转赠胡萝卜」一起消失 |

- **[P0] 支付 · 「申请成为服务商」是一条死路** — [`UserDetailView.tsx`](src/views/UserDetailView.tsx#L77) 写着「申请成为服务商后可看全」并链到 `/pay`，而 `/pay` 只有「查询订单」与「转赠胡萝卜」两块，没有申请按钮，`payApi.apply` / `payApi.update` 也都未接 — 普通用户按引导点进去，看到的是一个和自己无关的查单框；这个实例 `/api/pay/base` 还是 404，连查单框都会被隐藏，只剩下一句「没有开通支付服务商」 — `/pay` 在 404 时至少给一个「申请开通服务商」（`payApi.apply` 名称 + 描述两个字段），或把用户详情那句引导改成「联系管理员开通」。
- **[P1] 支付 · 仍是「查询 + 转赠」两块，不是财务页** — `payApi.close`（关单）、`testNotify`（测试回调）、`notifyEmail`（发通知）、`create`（发起支付）、`userCarrot`/`userSign`（查用户）全部未接 — 管理员出事时（订单卡在待支付、回调没到）无从下手 — 拆成 配置 / 对账（查单+关单+测试回调）/ 通知 三块。
- **[P1] 支付 · 转赠两个入口、两条语义** — 账号页与支付页各有一份，都调 `carrotApi.transfer`，而支付域的 `payApi.transfer` 从未被调用 — 同一动作两处入口、两个后端语义，账目对不上时无法判断走的是哪条 — 只保留一处（用户页），并明确走 `payApi.transfer` 还是 `carrotApi.transfer`。
- **[P2] 支付 · 404 时整页隐藏** — 用 `display:none` 藏掉全部卡片 — 「转赠」作为通用能力在未开支付的实例上凭空消失 — 转赠移出支付页（放用户页），支付页只留支付相关。

## 五、导航结构：内容(6) / 运营(4) / 系统(5) 是否过载

**先对齐口径**：`Sidebar.tsx` 里实际是 **内容 5 / 运营 4 / 系统 4**，另有一组「内容分区」（电影、剧集）2 项 —— 那 2 项全部指向 `/library`，所以按「链接数」算是 15，按视觉分组看像 6/4/5。差异就在这里。

**过载判断：项数不过载，分布过载。** 15 个链接对媒体服务器后台是正常量级（对比：同类后台常在 12~20）；问题在于「同一组里的东西不是同一类事」，以及「该有的组没有」。

- **[P1] 导航 · 概览仍在「内容」组** — 概览是全站首页，放在「内容」里既让「内容」语义模糊，又让它在视觉上只是「内容的第一项」 — 用户不容易把它当「今天从这里开始」 — 概览提到所有分组之上，独立置顶（不占组标题）。
- **[P1] 导航 · 回收站被放进「系统」** — 回收站的操作对象是影片和资源（内容域），使用时机是「刚删错了」——紧跟在删除动作之后，属于每周甚至每天 — 放在系统组最后第二项，等于让恢复路径绕一圈 — 移到内容组末尾，或更彻底：作为媒体库的第二个页签（`/library?tab=recycle`），因为它恢复的就是媒体库里的东西。
- **[P1] 导航 · 有 `/users/:id` 却没有「用户」入口** — 侧栏没有任何指向用户的东西，用户页只能从数据行跳进去（见 4.1） — 客服链路在导航层面不可达 — 新增「用户」组：用户查询（`/users` 列表 + 搜索）、封禁、邀请；把账号页的「封禁」「邀请」两个 tab 搬过去（它们本来就是「对别人的操作」，不该在「我的账号」里）。
- **[P1] 导航 · 上传仍在「运营」** — 上传 → 入库 → 详情 → 播放是同一条流程的四步，上传与媒体库/求片分属两组 — 每次都要换组找下一步；且仪表盘上「上传」只在快捷入口里出现 — 上传移到内容组，紧跟媒体库，改名「入库」。
- **[P2] 导航 · 「内容分区」是两行冗余** — 电影/剧集两项与媒体库的 tab 完全重复，且永远占两行 — 视觉噪音，还让人以为那是独立的库 — 删除，或改成真正的「分区管理」（若将来有纪录片/动漫等分区）。
- **[P2] 导航 · 角标位仍然空着** — `NavItem.tail` 已实现渲染但零赋值 — 待认领求片、待发货、封禁数都没有落点（与仪表盘缺待办是同一个问题的两半） — 求片/订单挂 `tail`，数据直接用 `useTodos()`。
- **[P2] 导航 · ⌘K 徽标是假的** — 搜索框已可用，但全仓没有 `metaKey` 监听，徽标只是装饰 — 习惯键盘的管理员按了没反应 — 加全局 keydown（20 行以内），或去掉徽标。

### 结构建议表

| 位置 | 项 | 角标 | 频次 | 与现状的差异 |
|---|---|---|---|---|
| 置顶（不属于任何组） | **概览** | 待办总数 | 每天 | 从内容组第一项提为独立置顶 |
| 内容（6） | 媒体库 | — | 每天 | 原位 |
| 内容 | **求片** | 待认领数 | 每天 | 从第 4 位提到第 2 位 |
| 内容 | **入库**（原「上传」） | 待上传/失败 | 每天 | 由运营组移入，改名 |
| 内容 | 片单 | — | 每周 | 原位（去掉假 chevron） |
| 内容 | 音乐 | 无资源数 | 每周 | 原位 |
| 内容 | **回收站** | 近期删除数 | 每周 | **由系统组移入**（恢复的是内容） |
| 运营（3） | **订单** | 待发货数 | 每天 | 从第 4 位提到第 1 位 |
| 运营 | 商城 | 待审店铺 | 每周 | 原位 |
| 运营 | 直播 | 异常源 | 每周 | 原位 |
| 用户（3，新增） | **用户查询** | — | 每天 | 新增（`/users` 列表 + 搜索） |
| 用户 | 封禁 | 封禁数 | 每周 | 从账号页 tab 搬来 |
| 用户 | 邀请 | — | 偶尔 | 从账号页 tab 搬来 |
| 系统（3） | 线路 | 异常数 | 每周 | 原位 |
| 系统 | 支付 | — | 偶尔 | 原位（建议改名「财务」） |
| 系统 | 账号 | — | 偶尔 | 只留 资料 / 胡萝卜 / 设备与安全 |
| —— | ~~内容分区（电影/剧集）~~ | — | — | **删除**（与媒体库 tab 完全重复） |

- 重排后：16 个链接 / 4 组 + 1 个置顶（现状 15 个链接 / 3 组 + 2 个冗余分区）。**项数只多 1，但「每天用的都在前两屏、对别人的操作有独立组、恢复紧挨内容」。**
- 备选（更省一屏）：把回收站做成媒体库的第二个页签（`/library?tab=recycle`），内容组回到 5 项、系统组 3 项、总数 13 + 1 置顶。代价是回收站不能再挂独立角标。
- 不建议：把「用户」塞进「系统」组。封禁/邀请是对人的操作，与线路/支付的服务配置是两类事，混在一起会重现「系统组什么都装」的老问题。
